{% comment %} Why the matching model runs here at all. This is what the rules are *for*: the whole point of converting a name to IPA is to let the matcher recognise it written in another script. Someone asked to spend an hour on a consonant table deserves to see the thing their hour buys, and to see it fail where it currently fails, rather than take our word for it. ⚠ The honest part, which is stated on the page and not only here. The model in the browser is a trained encoder: it reads characters, not the rules under review. The rules shaped the IPA it was *trained* against, so correcting one improves the training signal for the next model — it does not change what this encoder outputs today. Implying otherwise would be a demo that lies, and the first contributor to notice would be right to stop trusting the tool. {% endcomment %}
Does the matching actually work on this script?

Type a place name and a version of it in another script — the same place, written differently. The similarity score below is computed in your browser by the Symphonym encoder WHG uses for cross-script matching. Nothing is sent anywhere.

What this shows and what it does not. The encoder reads characters; it does not read these rules at run time. The rules produced the IPA it was trained against, so correcting them improves the signal the next model learns from — it will not change the score you see today. What the score does show, honestly, is where matching currently stands on this script.
